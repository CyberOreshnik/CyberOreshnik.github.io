01 / The research question

Revisit the assessment.
Preserve the reasoning.

The Personal Security Investigator v0.2 is a local browser-based test harness for exploring progressive evidence disclosure. It provides a fictional scenario, scheduled evidence packages, and a way for an investigator to record how a security assessment develops over time.

Its purpose is to examine the feasibility and usability of that process: when information becomes eligible, what the investigator concludes, why the conclusion changes, and how the available evidence can be traced to each saved assessment.

The reviewed version does not scan devices, connect to accounts, or generate an independent security verdict. Its assessments are entered by a human operator. No study outcomes, detection-performance estimates, or claims of efficacy are reported here.

02 / Experimental methodology

A proposed workflow.
A bounded prototype.

The intended feasibility workflow uses a fixed fictional scenario with six scheduled evidence releases. This is a description of the prototype and a proposed study approach, not evidence that a validated experiment has been completed.

  1. Define the run. Identify the scenario, version, investigator role, clock mode, and recording procedure before starting.
  2. Establish T+0. Begin with the release of the first evidence package. T+0 is not the alleged intrusion start, case-open time, or the time an assessment is saved.
  3. Release evidence progressively. Review only material eligible at the current scenario checkpoint. The intended interface offers controlled step-through and real-time scheduling; clock-mode wiring in v0.2 remains a development issue.
  4. Record and reassess. Save a classification and rationale, stating uncertainty and alternative explanations. Revisit the judgment as further evidence becomes available.
  5. Preserve the record. Export the run and checkpoint history for private review. Define scoring, timing rules, and validation procedures before using records to support research conclusions.
03 / Progressive evidence disclosureSix scheduled releases

The evidence clock.

Scenario time

Determines when a package is eligible for review.

Wall-clock time

Measures actual elapsed implementation time. It must be distinguished from scenario time and pause duration.

Checkpoint-save time

Records when an investigator saves an assessment; it may occur after a scheduled release.

A step-through run is not a 47-second wall-clock detection result. Browser scheduling, background-tab throttling, and unresolved clock behavior limit timing interpretation.

04 / Investigator assessments

A conclusion.
And its explanation.

MALICIOUS
The investigator judges the released evidence to support a malicious interpretation.
BENIGN
The investigator judges the released evidence to support a legitimate interpretation.
UNCERTAIN
The available evidence does not justify a sufficiently definite interpretation.

These are investigator-entered classifications, not automatic detections or verified ground truth. The interface also permits optional subjective intrusion-probability and confidence estimates. These are distinct fields; neither is established as calibrated.

A rationale is required. It should connect the assessment to released evidence, distinguish observation from inference, identify unresolved questions, and consider alternative explanations. A change in assessment should remain understandable alongside the earlier record.

05 / Traceability and audit records

What was available.
What was concluded.

The prototype associates saved assessments with the identifiers of released evidence packages and a snapshot of the release log. Records include classification, rationale, optional probability and confidence, scenario time, save timestamp, and wall-clock elapsed time. Release records distinguish scheduled from recorded release times; pause and resume actions have a separate log.

The interface provides run JSON and checkpoint CSV exports. Later releases do not rewrite an earlier assessment through the normal interface. This is an in-memory history, not a tamper-evident or independently secured audit ledger. Refreshing or closing the page can discard the live state, so preservation requires an explicit export.

Private study documentation is maintained separately from the website for the protocol, version history, methodology, validation plan, and experimental records. The working prototype, scenario payloads, and raw research records are not hosted or offered for download here.

06 / Limitations and development status

Feasibility first.
Validation remains ahead.

Development status: Experimental v0.2

  • The supplied package contains one fictional scenario. It cannot establish performance across representative malicious and benign cases.
  • Assessments are human-entered. The prototype does not independently verify sources, detect compromise, or demonstrate autonomous response capability.
  • Source inspection identifies incomplete clock-mode initialization: the selector is not consistently carried into run state and exported protocol metadata. Pause-time accounting also requires correction and verification. Timing comparisons are not presently defensible.
  • Evidence gating is a presentation mechanism. Future package contents are bundled in the local client source, so this is not secure or blinded evidence delivery.
  • Local exports and interface history do not establish cryptographic integrity, durable storage, independent review, or reproducibility on their own.
  • No independent validation, calibration, production readiness, or improved detection performance is established.

Planned validation

Next steps are to resolve the clock and record-consistency issues, test release eligibility and snapshot preservation, freeze a reviewable protocol and scenario set, predeclare scoring and exclusions, and evaluate repeatability with independent review. These steps are planned work, not completed validation.
